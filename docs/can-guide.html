Core idea in one sentence

CAN is a robust, message-based, multi-node serial bus designed for embedded systems where many devices must communicate reliably with low wiring cost and deterministic behavior.

Key strength: CAN uses arbitration on the bus so that multiple nodes can transmit without a central controller, and the winner of contention continues sending its message.

1. What CAN is and why it matters

Controller Area Network, or CAN, is a communication standard created for automotive and industrial systems. Its design goals were simple but powerful: allow many controllers to exchange messages over a shared two-wire bus with high reliability, low overhead, and deterministic timing.

In a modern embedded project, CAN is useful whenever you have multiple microcontrollers, sensors, actuators, or boards that need to share data without using a huge number of dedicated wires. It is common in vehicles, robotics, industrial automation, motor controllers, battery management systems, and test equipment.

Why CAN is popular

  • Multi-node communication with just two wires
  • Built-in arbitration without a central bus master
  • Excellent reliability for noisy environments
  • Very low protocol overhead compared with higher-layer networking stacks
  • Widely supported by MCUs, toolchains, and hardware

What makes it different from UART or SPI

  • UART is point-to-point and simple but not multi-node
  • SPI requires a dedicated chip select line per device
  • CAN allows many nodes to share the same bus naturally
  • CAN supports collision resolution at the bit level

2. How CAN works under the hood

CAN is message-oriented rather than byte-stream-oriented. Instead of sending a continuous stream of bytes like UART, each node transmits packets called frames. These frames contain identifiers, control bits, data, and error-checking information.

The bus in practice

The bus is physically two wires: CANH and CANL. They carry differential signals. The receiver interprets the voltage difference between the wires rather than the absolute voltage on a single wire. That makes CAN resistant to noise and common-mode interference.

Important concept: CAN nodes do not transmit in a fixed time slot. They compete for the bus using arbitration. The node that wins continues transmitting its frame.

Core protocol concepts

  • Arbitration: resolves which node gets to send when multiple nodes start transmitting at once.
  • ACK: confirms that at least one node received the frame correctly.
  • CRC: detects bit errors in the transmitted frame.
  • Error handling: nodes can signal errors and possibly enter bus-off state if repeated errors occur.
  • Bit stuffing: inserted bits keep the stream from staying too long in one state, helping with clock recovery.

3. Frame types and structure

The most important frame is the data frame. CAN also supports remote frames and error frames, though most practical applications use data frames.

Standard data frame layout

SOF | Identifier | RTR | IDE | DLC | Data bytes | CRC | ACK | EOF | IFS

The exact field names vary slightly by implementation, but the overall idea is the same: an identifier, control bits, payload, integrity checks, and delimiters.

Common frame fields

Field Meaning
SOFStart of frame bit
IdentifierMessage ID used for arbitration and filtering
RTRRemote transmission request bit
IDEIdentifier extension bit, marks standard vs extended format
DLCData length code, from 0 to 8 bytes
DataThe actual payload bytes
CRCCycle redundancy check for error detection
ACKReceiver confirms valid reception
EOFEnd-of-frame delimiter

Standard vs extended frames

  • Standard frame: 11-bit identifier
  • Extended frame: 29-bit identifier
  • Extended frames are more flexible but slightly more overhead
  • Most beginner projects begin with standard frames

4. Physical layer and transceivers

The CAN controller inside the MCU is not the whole bus interface. The controller drives the bus through a transceiver. The transceiver converts the MCU’s logic-level signals into the differential CANH/CANL bus signaling required by the standard.

Why the transceiver matters

  • It provides the correct differential voltage levels
  • It improves noise immunity
  • It ensures the bus is properly driven and received
  • It protects the MCU from bus transients

Termination and topology

CAN is normally a single-ended differential bus with a termination resistor at each end of the physical bus. The standard value is usually 120 ohms across CANH/CANL at the two ends of the bus.

Rule of thumb: If you have a short bus with only two devices, ensure the transceiver side is correctly terminated and that the common ground reference is adequate.

5. Bit timing and baud rates

CAN timing is more subtle than many beginner UART examples. Each bit is segmented into multiple time quanta. The controller uses propagation, phase, and synchronization segments to sample the bus reliably at the right moment.

Key timing concepts

  • BRP: baud rate prescaler
  • TS1: time segment 1
  • TS2: time segment 2
  • SJW: resynchronization jump width
CAN bit timing is derived from:
- system clock
- BRP
- TS1
- TS2
- SJW

Typical result: 500 kbps or 1 Mbps bus speeds

For a beginner setup, using a standard target such as 500 kbps is often easier than trying to optimize everything from scratch. If your clock is different from the expected value, the timing register values must be recalculated.

6. STM32F407 CAN setup

This repository’s firmware uses CAN1 on the STM32F407 with PB8 and PB9. Those pins are mapped to CAN1 RX and CAN1 TX respectively through the MCU’s alternate function system.

Recommended pin mapping

  • PB8 → CAN1_RX
  • PB9 → CAN1_TX

Hardware wiring example

STM32F407 PB8  -> transceiver RX pin
STM32F407 PB9  -> transceiver TX pin
Transceiver CANH -> CAN bus CANH
Transceiver CANL -> CAN bus CANL
Ground shared between MCU and transceiver

Register-level overview

1. Enable GPIOB and CAN1 clock
2. Configure PB8/PB9 as alternate function
3. Enter initialization mode
4. Set bit timing
5. Configure receive filter
6. Leave initialization mode
7. Enable transmission
Example of the core idea in C:
CAN1->MCR |= CAN_MCR_INRQ;   // enter initialization mode
CAN1->BTR = ...;            // configure bit timing
prvCanConfigureRxFilter();  // accept incoming frames
CAN1->MCR &= ~CAN_MCR_INRQ;  // leave initialization mode

7. Using CAN in FreeRTOS

The CAN implementation in this project is intentionally split into FreeRTOS tasks. That makes the firmware more organized, easier to reason about, and safer than placing all CAN I/O directly in the main loop.

Why tasks help

  • Keep the main function simple
  • Avoid blocking the whole firmware while waiting for a mailbox or FIFO state
  • Separate transmit and receive activity into dedicated tasks
  • Make debugging and timing analysis easier

Recommended task structure

Task A: periodic transmit task
Task B: periodic receive task
Task C: application logic / state machine
Task D: LED or diagnostics task

Transmit task pattern

static void CanTxTask_250ms(void *pvParameters) {
    TickType_t lastWake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(250);

    for (;;) {
        prvCanTransmitStdFrame(0x123, payload, 8);
        vTaskDelayUntil(&lastWake, period);
    }
}

Receive task pattern

static void CanRxTask_100ms(void *pvParameters) {
    TickType_t lastWake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(100);

    for (;;) {
        while ((CAN1->RF0R & CAN_RF0R_FMP0) != 0U) {
            // read FIFO frame
            // store ID, DLC, and payload
            // release FIFO mailbox
        }
        vTaskDelayUntil(&lastWake, period);
    }
}
Scheduling rule of thumb: keep CAN tasks periodic, short, and predictable. Avoid long blocking loops inside the CAN tasks unless the design explicitly requires them.

8. Troubleshooting and best practices

Common symptoms

  • No traffic appears at all -> likely missing transceiver or wrong pins
  • Frames transmit but never ACK -> bus termination or grounding issue
  • Frames are received inconsistently -> wrong bit timing or poor wiring
  • Receive FIFO never fills -> filter configuration too restrictive

Practical checks

  • Confirm your transceiver wiring and power
  • Verify 120 ohm termination at the bus ends
  • Confirm the CAN bit timing matches the bus
  • Use a logic analyzer or CAN dongle for debugging
  • Inspect the receive and transmit status bits

Best practices

  • Start with a simple standard frame and a single known ID
  • Use 500 kbps or 1 Mbps for early experiments
  • Keep payload sizes small and fixed
  • Do not mix too many responsibilities inside the same task
  • Prefer queues for passing received CAN data to application tasks

10. Final thoughts

CAN is one of the most useful communication protocols in embedded systems because it gives you robust, shared, multi-node messaging with surprisingly simple wiring. Once you understand the basics of arbitration, ACK, CRC, filtering, and timing, you can build reliable systems that scale from a single board to a full distributed control network.

For this STM32F407 project, the current implementation already provides a practical foundation: transmit a standard frame, receive frames into FIFO0, and coordinate both activities from FreeRTOS tasks. That is enough to start experimenting, learning, and then evolving the design into a more production-ready driver.
